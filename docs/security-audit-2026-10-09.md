# 小鱼干与认证系统安全审查报告

审查日期：2026-10-09（北京时间）

审查基线：`f61acd81`

范围：登录、注册、角色权限、每日签到、小鱼干余额与流水、转账与付款、只读凭据、练手盘、OAuth、数据库与文件读取边界。

## 1. 结论

**排除已知的收款回调 SSRF 防护绕过后，本轮确认 6 项应用层安全缺陷，其中 2 项建议优先修复；另发现一项与 Windows 部署有关的严重依赖风险。**

没有在本轮审查中找到“无需凭据即可冒充管理员”“普通用户绕过 core 档位直接领取签到奖励”“同日重放或并发签到重复发鱼”“负数转账凭空增加余额”“网络直接下载 SQLite”这样的可成立攻击链。这不等于系统没有安全漏洞：匿名 OAuth 请求可以绕过计算限频；自助改密码不能撤销已建立的讨论长连接；IP 信任、登录并发和 OAuth 撤权也存在缺口。

| 编号 | 问题 | 优先级 | 验证状态 |
| --- | --- | --- | --- |
| A1 | OAuth 错误客户端密钥请求在限频前执行 scrypt | P1 | 实际 HTTP + 真实密码计算复现 |
| A2 | 自助改密码未断开旧 SSE，旧连接继续收到新私聊 | P1 | 实际 HTTP + 独立测试库复现 |
| A3 | 客户端可伪造用于 IP 限频的请求头 | P2 | 真实路由探针复现；线上影响依赖代理配置 |
| A4 | 登录先查额度、失败后记数，并发可越过剩余额度 | P2 | 真实 SQLite + 真实密码计算复现 |
| A5 | 正确密码的付款确认等入口缺少计算请求限频 | P2 | 真实付款路由 + 真实密码计算复现 |
| A6 | 停用 OAuth 应用后，旧 access token 仍可访问 userinfo | P2 | 实际 HTTP + 独立测试库复现 |
| D1 | Next 15.5.20 落在 Windows 未认证 RCE 公告影响范围 | 严重，条件成立时优先处理 | 版本与官方公告核对；未执行 RCE 利用 |

P1/P2 是本次修复排序，不是已经测出的线上 CVSS 分数。本轮没有进行线上压测，不能据本地计算耗时宣称生产服务器已经可以被某个确定请求数打瘫。

## 2. 方法与边界

- 源码审查：从网络路由追到认证、权限、事务、密码计算、限频和文件读取，检查输入是否能影响操作者、角色、日期、金额及 SQL。
- 隔离测试：使用 `tests/.tmp/test-*` 独立 SQLite，测试工具既检查配置，也检查 Prisma 实际连接路径；没有使用真实用户、真实密码或生产数据库作为攻击目标。
- HTTP 验证：当前源码启动独立的 Next 开发服务器，**只监听 `127.0.0.1` 的临时端口**，使用独立构建目录与测试库。Webhook 投递、行情轮询、行情流和强平循环均关闭。该验证不等于生产 nginx、CDN、WAF 或 `next start` 部署验收。
- 已有回归：10 个相关既有测试文件、395 项测试通过；另外 10 项临时攻击探针完成。HTTP 验证记录了 12 组结果。
- 文件边界：检查网络可达 SQL 与文件读取；另对文档、头像、故事模块做 24 项恶意路径输入检查。
- 已知收款回调 SSRF 不计为新发现，也没有以它为跳板扩展攻击。

## 3. 已确认问题

### A1. OAuth 错误密钥可无限触发昂贵密码计算（P1）

**代码位置**：`src/app/api/oauth/token/route.ts:41`、`:52`；`src/lib/oauth.ts:184`、`:198`；`src/lib/password.ts:66`。

令牌接口先调用 `authenticateClient()`。对于存在且启用的 `client_id`，鉴权会执行 scrypt 校验 `client_secret`。错误密钥在这里返回失败，路由随即返回 401，根本到不了后面的每分钟 60 次限频。即使密钥正确，限频检查也仍然发生在密码计算之后。

**攻击前提**：知道一个有效且启用的 `client_id`；它是 OAuth 授权 URL 中的公开标识，不要求知道客户端密钥，也不要求登录本站。

**实测**：隔离 HTTP 服务器连续接收 65 次错误密钥请求，65 次全部返回 401，没有一次 429，耗时约 10.36 秒。另一个直接调用路由、包装真实密码验证的探针记录到 65 次 scrypt 调用。测试用的哈希参数为本站当前默认 `32768:8:1`，单次主要工作内存约 32 MiB。

**影响**：匿名攻击者可以持续占用密码计算线程池和 CPU。攻击路径不依赖 A3 的伪造 IP，也不受登录失败预算约束。并发上限和线上瘫痪阈值尚未测量。

**建议**：在任何数据库鉴权及 scrypt 之前，对可信来源 IP、客户端标识和进行中的计算数量实施限制；失败请求必须计数。保留鉴权后的业务额度，但不能把它当成计算保护。nginx 入口限频可作为额外防线。

### A2. 自助改密未撤销已有讨论 SSE（P1）

**代码位置**：`src/lib/user-service.ts:646`；`src/app/api/auth/change-password/route.ts:27`；`src/app/api/chat/stream/route.ts:31`、`:74`、`:87`；`src/lib/chat-bus.ts:101`。对照：`src/lib/admin-user-service.ts:539`。

`changeOwnPassword()` 更新密码及 `sessionVersion`，但没有调用 `kickUser()` / `kickTopbarUser()`。讨论 SSE 只在连接建立时认证，随后按用户 ID 订阅；消息投递不会重新核验会话版本。改密路由清除当前浏览器 Cookie，也无法关闭攻击者已建立的连接。

**攻击前提**：攻击者已经获取受害者的有效会话，并在受害者改密前建立讨论 SSE。此问题不是凭空获得会话，而是受害者的改密止血动作不能完成撤权。

**实测 HTTP 链**：

1. 用测试用户的旧 Cookie 建立 `/api/chat/stream`，返回 200。
2. 用户自助修改密码，返回 200，数据库会话版本递增。
3. 用同一旧 Cookie 新请求 `/api/checkin`，返回 401，证明新请求撤权有效。
4. 另一测试用户在既有私聊发送一条新消息，返回 200。
5. 改密前建立的旧 SSE 仍收到这条**改密后发送的私聊正文**。

**影响**：受害者认为改密已使旧会话失效，攻击者却仍能通过旧连接继续接收私聊，直到连接断开。顶栏总线探针也证实旧订阅未被主动关闭。管理员重置密码与强制下线已经使用成对踢连接逻辑，自助改密漏掉了这一环。

**建议**：自助改密提交成功后，调用 `kickUser(userId)` 与 `kickTopbarUser(userId)`。进一步核对会话版本更新是否应使用原子 `increment`，以及认证、建流和撤权之间的并发边界。补一条“旧请求 401 且旧流收不到新私聊”的回归断言。

### A3. IP 限频信任可控请求头（P2）

**代码位置**：`src/lib/request-ip.ts:37`；`src/lib/credential-auth.ts:55`；`docs/deploy.md:388`、`:389`。

`clientIp()` 优先接受任意 `CF-Connecting-IP`，否则使用 XFF 第一项。部署文档的 nginx 示例设置了可信的 `X-Real-IP`，但应用不读取它；XFF 使用 `$proxy_add_x_forwarded_for`，保留客户端自带的首项，示例也没有清除或覆盖 CF 头。

**实测**：把 `203.0.113.7` 的登录 IP 失败桶预填至 300 次后，同一 IP 的请求得到 429；添加一个新的 `CF-Connecting-IP`，或把新的伪造值放在 XFF 首项，请求均变成 401，进入正常鉴权流程。已有真实 IP 的 `X-Real-IP` 不改变结果。

**影响与前提**：攻击者能让这些头原样到达应用时，换头即可换 IP 桶，降低批量撞库与匿名重计算请求的成本。用户名桶仍然存在，不能把此项单独描述为“任意单账号无限破解”。若 Cloudflare 是唯一入口、覆盖 CF 头且源站严格限制访问，此利用条件可能被阻断。本轮未验证线上入口及源站防火墙。

**建议**：明确代理信任模型；应用读取由可信 nginx 覆盖的 `X-Real-IP`，校验合法 IP；代理清除不可信 CF/XFF 值；源站监听与防火墙限制直接访问。不能仅凭收到某个请求头就认定它由可信代理写入。

### A4. 登录失败限频存在并发预检窗口（P2）

**代码位置**：`src/lib/credential-auth.ts:58`、`:66`、`:79`；`src/lib/rate-limit.ts:85`、`:99`。

登录先调用 `isRateLimited()` 只查不记，然后等待数据库及密码校验，失败后才 `recordRateLimitHit()`。同时到达的请求都可能在前一批请求记录失败前通过检查。攻击者不必伪造 IP 就能超用当前窗口剩余预算。

**实测**：把一个真实测试用户的失败桶预填到 99/100，同时提交 8 次错误密码。8 次均完成密码验证并返回 401；后续串行请求才返回 429。当前设计本应只剩一次预算。

**影响**：一次并发突发可以越过失败额度并放大密码计算；这不是已经证实的“持续无限绕过”，突发完成后桶会超限。

**建议**：在异步工作前原子预留尝试预算，成功后按产品语义释放；或把“失败次数限制”与“所有密码计算请求的速率/在途数量限制”分开实现。释放和失败应在同一生命周期中处理，避免异常泄漏配额。

### A5. 正确密码请求绕过计算保护（P2）

**代码位置**：`src/app/api/fish/market/pay/route.ts:50`、`:56`；`src/lib/credential-auth.ts:79`；`src/lib/fish-market-service.ts:260`。相关入口：`src/app/api/fish/tokens/route.ts:81`、`src/app/api/auth/login/route.ts:28`。

付款接口先做密码确认，再校验转账金额。共享认证内核只有失败才消耗预算；正确密码的请求不计数。无状态鱼干 API 的“成功也计数”保护不适用于此会话付款路径。

**实测**：普通零余额测试账号携带会话和正确密码，连续提交 25 次金额为 0 的付款请求。25 次都先通过密码校验，再因金额不合法返回 400；没有 429，没有任何余额或流水变化。超过无状态鱼干接口的 20 次/分钟计算预算，也不会被该预算拦截。

**影响**：拥有一个普通账号及自己的密码即可重复占用密码计算资源，不需要鱼干、core 身份或真实收款人。成功登录、签发只读凭据等入口也存在相同的正确密码计算预算缺口；凭据签发另无总量上限，会增加持久化数据量。后者本轮仅作源码观察，未做大量写入。

**建议**：为所有昂贵密码计算增加独立的速率及在途限制。把纯输入合法性检查提前；不要把余额不足、转账额度或幂等重放当成密码计算的上限。可同时限制单用户有效凭据数量并分页列表。

### A6. 停用 OAuth 应用没有使旧令牌失效（P2）

**代码位置**：`src/lib/oauth.ts:321`、`:459`；`src/app/api/oauth/userinfo/route.ts:21`；`src/app/admin/oauth/ApplicationRow.tsx:37`。

应用停用写入 `disabledAt`，客户端新鉴权会检查它；但 `validateAccessToken()` 只检查令牌存在、吊销和到期，没有核对所属应用是否停用。`userinfo` 也没有补这道检查。管理界面明确提示“禁用后该应用的所有现有 token 也会被拒绝”，实际行为不满足该承诺。

**实测**：为隔离测试应用签发 profile 令牌，然后在测试库把应用置为停用；用旧 Bearer 访问 `/api/oauth/userinfo` 仍返回 200 和测试用户 ID。

**影响**：站长禁用恶意或泄露密钥的应用后，该应用已有令牌仍能读取已授权 profile，直到吊销或到期；当前令牌期限为 90 天。当前 scope 不包含鱼干写入或管理员操作，不能据此宣称接管账号或刷鱼。

**建议**：令牌校验实时查询应用停用状态并拒绝；可同时在停用事务中吊销其令牌。回归测试应使用真实应用行，从“启用时 200”到“停用后拒绝”，再验证重新启用时的预期恢复语义。

## 4. 严重依赖风险：Windows 部署条件

`package-lock.json:4408` 与实际安装的 Next 均为 **15.5.20**；React 为 **19.2.7**。

Next 官方公告 [GHSA-p293-qw3h-jr36 / CVE-2026-75604](https://github.com/vercel/next.js/security/advisories/GHSA-p293-qw3h-jr36) 把 `>=13.4 <15.5.24` 列为影响范围：使用 Windows 文件系统、Pages/App Router 且未启用 Cache Components 的服务器可能遭受未认证远程代码执行，15.5.24 修复。

本项目采用 App Router，当前版本处于该区间，本地审查环境也是 Windows。因此，**若该版本部署在攻击者可访问的 Windows 主机上，应按严重 RCE 风险处理**。若生产确为 Linux，此项的 Windows 前提不成立。本轮没有核实线上操作系统，也没有执行 RCE 利用；不能把公告核对写成“线上已经可远程执行代码”。一旦 RCE 条件成立，进程能访问的 SQLite、签名密钥和账户数据都将受到威胁，即使业务 API 的权限检查正确。

建议保持仓库既有 **Next 15** 大版本边界，更新到包含相关修复的受支持 15.5 补丁版，再执行构建与部署验收；不要安装 `next@latest` 导致跨到 16。15.5.24 是此公告的最低修复版本，不代表它涵盖截至审查日所有后续公告。

另核对了 [Next July 2026 安全公告](https://nextjs.org/blog/july-2026-security-release)。本项目当前源码没有实际 Server Action / `use cache`，旧投票 Server Action 只剩说明注释，也没有动态外部目标主机 rewrite 或单 locale i18n 配置。因此，没有把这些缺少项目利用前提的公告直接登记为本项目已确认漏洞。图像优化的 AVIF 公告也需要结合实际 sharp/libheif 与路由暴露情况，本轮没有确认它构成可利用链。

## 5. 重点攻击方向的结果

| 方向 | 本轮结果 | 主要证据 |
| --- | --- | --- |
| 冒充管理员 | 未发现直接绕过 | JWT 验签；角色从数据库读取；注入 role 不提升权限；匿名管理员列表 403 |
| 注册批量字段注入 | 已阻断本轮输入 | 注入 owner、余额、ID、会话版本，建出的账号仍为 user、余额 0 |
| 无邀请码获得 core | 未发现绕过 | 注册根据服务端邀请码决定档位；邀请码占用采用条件写，注册核销与建号同事务 |
| 非 core 签到 | 已阻断 | 匿名 401；普通用户即使有文章也 403 |
| 缺少本人未删文章签到 | 已阻断 | 只剩软删文章、或只有他人文章，均 403 |
| 客户端指定日期、用户、奖励 | 已阻断 | HTTP 注入未来日期、站长 ID、超大奖励仍只给当前会话用户当日 3 条 |
| 同日并发重复发鱼 | 未出现 | 30 次同时打卡仅一行签到、一笔 3 条流水，余额与账本一致 |
| 负数、非有限金额、超精度 | 未发现直接刷鱼 | 转账校验与既有财务回归；条件扣减、双边流水、幂等记录同事务 |
| 只读令牌转账 | 已阻断 | 真实路由返回 403，无余额或流水变化 |
| 交易仓位越权、重复兑现 | 未发现成立链 | 仓位所属用户检查、状态条件写、现取成交价；相关 API 与财务回归通过 |
| CSRF | 本轮跨站输入被阻断 | 带攻击站 Origin 的实际 HTTP POST 返回 403 |
| 网络直接读库 | 未发现成功链 | 两个常见数据库路径、`.env`、schema HTTP 404；网络 SQL 未见请求输入拼接 |
| 文件路径穿越 | 本轮输入未越界 | 文档/头像/故事 24 项输入检查；编码穿越头像 HTTP 返回生成头像，没有 SQLite 内容 |

余额公开查询是仓库明确设计，不能把“能查他人余额”单独列为越权。非核心账号能够收取转账也不等于获得新增发鱼渠道。禁言后的已有仓位平仓、只读凭据改密后仍有效，均有明确产品语义，未作为漏洞报告。允许 iframe 嵌入也不是本轮应补 `X-Frame-Options` 的理由。

## 6. 并发打卡的可用性观察

30 个同账号并发签到的独立复测返回：**1 个 200、11 个 400、18 个 500**，日志包含 Prisma `P2028` 与事务不可用错误。最终只有一行签到和一笔 3 条鱼干流水，账本不变式通过。

最初临时探针要求另外 29 个请求全部返回 400，因上述 500 而失败；后续将断言聚焦到“只有一次发鱼且账本一致”，同时保留 500 现象，没有修改业务实现。395 项既有回归均通过，不能用“测试通过”掩盖这里的可用性退化。

此结果说明重复领奖防线有效，但并发重复请求的错误处理与写事务开销仍值得改善。它不证明攻击者已能破坏账本或影响其他账号，更不证明线上全站拒绝服务。建议评估在数据库唯一约束之外增加按用户的在途合并/重复请求早退，并对事务超时返回做一致处理；数据库约束仍须保留。

## 7. 处理顺序与后续验收

1. 先修 A1 的密码计算前置保护，以及 A2 的自助改密断开旧连接；如存在公网 Windows 部署，同步处理 D1。
2. 明确代理信任配置，修 A3；再统一密码计算入口的速率与并发保护，修 A4/A5。
3. 修 A6 的应用停用撤权；补齐应用令牌生命周期测试。
4. 单独评估签到并发超时，不改变一天一次和记账事务的不变式。
5. 上线前验证真实 nginx/入口请求头、源站访问限制、生产版本与操作系统、真实 `next start` 下的改密撤流，以及低强度限频验收。

本报告记录的是本轮本地代码审查和隔离实测结论；**没有修复上述业务缺陷，没有对生产站进行攻击、改库或压测**。未发现某类攻击链不是对全部历史代码、全部依赖及线上配置的安全保证。

### B1. 申诉列表接口的档位与信息面（P2）

**代码位置**：`src/app/api/admin/appeals/route.ts:7`（`hasAdminRights`）对照 `src/app/admin/appeals/layout.tsx`（`requireOwner`）；`src/lib/admin-appeal-service.ts:54`（`APPEAL_SELECT`）、`:88`（`mapAppealRow`）。

`APPEAL_SELECT` **无条件**投影 `log.targetUser`，且**根本没有 select** `log.hideTarget`，服务层因此无从按匿名口径抹掉当事人；`appellant`（申诉人）也一并下发。对匿名评论的处置日志而言，`createAppeal` 强制只有被处理的目标本人能申诉，所以申诉人就是那位匿名作者 —— 拿到列表即还原真身。

**影响与前提**：真正可行动的点是**档位不一致**——裁决是站长专属（`adjudicate` 判 `isOwner`），对应页面也是站长档，但列表 API 只要求 admin。需注意：本仓设计**有意**保留「管理员能从日志里查到原作者」（`targetUserId` 始终为真身，供运维与管理员查证），所以「管理员看得到真身」本身不违反承诺；被破坏的是**面向更宽档位的信息面与页面不匹配**这一点。

**建议**：GET 与页面同档（`isOwner`）；或像 `getLogDetail` 一样，对 `hideTarget` 的日志把 `appellant` 与 `targetUser` 一并抹掉（需把它们补进 `select`）。回归测试应覆盖「匿名评论处置日志在 admin 档下不出真身」。

### B2. `/api/checkin` 缺禁言闸（P2）

**代码位置**：`src/app/api/checkin/route.ts:39-46`。POST 只判「登录 + core+ + 本人有未软删文章」，**无 `isCurrentlyBanned`**。

对照：`market/transfer`、`market/pay`、`market/rent`、`blogs/[id]/feed`、`trade/buy`、`tokens` POST **全部**带禁言闸；`src/app/api/fish/trade/buy/route.ts:33-38` 更写明了本站口径——「禁言不开新仓，也就没有新的赚取」。签到是**恒定 3 条/天**的新增赚取渠道（`src/lib/checkin-service.ts:50`），因此被禁言的 core+ 用户每天仍能 +3。

**影响与前提**：需要「先被禁言」这一前提，因此不是「非禁言用户的铸币口」，而是**禁言这道控制漏掉了他唯一的主动赚取渠道**。`checkin-service` 头部只列了 core 与「发过文章」两道门，未提禁言；是否属于有意，取决于产品口径——但它与 buy 的口径直接矛盾，倾向于疏漏。

**建议**：POST 增加 `isCurrentlyBanned(user)` → 403（GET 为状态读，可沿用现有「不拒、回 `can_check_in`」的写法）。补一条「被禁言用户 POST 签到 403 且余额不变」的回归。

### B3. `restoreComment` 授权在写之后（P3，当前仅 CLI 可达）

**代码位置**：`src/lib/comment-service.ts:941-948`。`restoreCommentRow(commentId)` 是独立已提交事务（`:905`），其后再判 `row.authorId === actor.id` 或管理员权限。

**影响**：恢复在鉴权前已落库；非授权 actor 会「先恢复、后 403」。当前唯一调用方是运维 CLI（`scripts/cli/commands/comments.ts:229`），正常路径 actor 为 owner，现实影响低；但 CLI 支持 `--as <user>`，且**一旦将来有 HTTP 路由接 `restoreComment`，即成为可远程利用的授权绕过**。对照 `softDeleteComment`（`:802-808`）是在同一事务内先判权的正确写法。

**建议**：把 author/管理员 + reason 校验移到 `restoreCommentRow` 之前。

### B4. `feedBlog` 允许自投喂（P3，不铸币）

**代码位置**：`src/lib/feed-service.ts:131-237`，无 `author ≠ feeder` 判定。自投喂时两笔 `postEntry`（扣自己 `-units`、加自己 `+units`，`:180`、`:191`）**净额为 0，不产生新鱼**；但 `blog_feeds` 行与 `Blog.fishCount`（`:236`）照加，于是 core 用户可零成本抬高自己文章的显示投喂数、并出现在投喂者名单里。受「单篇每人 ≤ 5」上限（`:217`）约束，不能无限刷。对照 `transferFish`（`fish-market-service.ts:289`）明确禁止自转账。

**建议**：`feedBlog` 增加 `userId === blog.authorId` → 400。

### B5. `/api/oauth/revoke` 的 CSRF 豁免与 cookie 鉴权（P3，当前不可利用）

**代码位置**：`src/middleware.ts:63-67`（豁免名单）与 `src/app/api/oauth/revoke/route.ts:41-49`。中间件注释要求加入豁免名单的端点「必须由 client_secret / token 自身承担鉴权」，但 `revoke` 存在一条走会话 cookie 且**改变状态**（吊销令牌）的路径。当前不可利用：跨站 POST 需要受害者那条 32 字节原始令牌（不可猜），且会话 cookie 为 `SameSite=Lax`，跨站 POST 不会携带它。

**建议**：从豁免名单移除，改由 bearer/client 鉴权。

### 本轮核实为「干净」的方向（负面对照）

- **任意文件读取 / 路径穿越 / SQLi**：未发现可利用路径。所有取 URL 段拼路径的读口，落盘路径均由服务端数据重建——图片/音频按 DB 主键 `id` 取行、贴纸按 readdir 清单映射、头像框按 `FRAME_KEYS` 白名单、文档按 `DOC_ENTRIES` 表查、story 走严格段名过滤；`instance/` 不在 `public/` 下，仓库未使用 `next/image`，`db.db` 无法经静态服务或图片优化器触达；原始 SQL 除上列整数 id 一例外均参数化。
