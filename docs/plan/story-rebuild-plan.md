# 故事区重做计划

调研日期：2026-10-31。状态：**方案完成，工具、内容重编与新版页面均未实施**。

这次重做要交付两样东西：一个能持续发现、整理作品的编辑流程，以及一个值得放在网站首个入口的故事区。只有小说列表，页面仍会停留在旧状态；只有漂亮页面，新投稿仍会继续积压。

建议采用 **人工策展的首页 + 按作品定制的版本 + 共用的阅读基础设施**。页面结构、章节顺序、配图位置和推荐顺序由编辑确认；正文保持可追溯的独立内容文件。先做出 3 个完整的作品样板，再逐批扩大。**不把“整理完全部历史文章”设为新版上线的前置条件。**

## 2. 调研后应当先做的判断

### 2.1 真正的规模与难点

本地快照中有 6,196 条博客记录，其中未软删除 4,909 条，来自 214 个作者账号，正文原始字符合计 27,091,994。未删除文章中，“文学&艺术”栏目只有 548 条，不能用它代替全站筛选。

文章原始长度中位数是 113 字符，但 207 条超过 30,000 字符，这部分占全部正文字符约 83.7%。因此要同时处理大量极短内容和少量超长内容。标题、栏目和开头只能用来安排阅读顺序，不能据此永久排除小说。

旧故事区有 8 个顶层合集，包含 265 个 Markdown 文件与 7 个 Cattca 文件。其中 Life 精选集占 231 个 Markdown 文件。**这些是文件数，不是独立作品数**；长篇、合集、单章和完整短篇现在混在同一层概念里。

还有两件事比页面风格更早影响方案：

- 未删除博客中有 4,907 条为 `internal`，只有 `link`、`public` 各 1 条。站长能读到，不代表可以把全文、摘要、标题或引用资源放到公开故事页。
- 旧故事与博客不是一对一关系。去除文件头和空白后，只有 8 个 Markdown 文件能与现存博客正文完全匹配。其余不能据此说“没有来源”：可能有合章、编辑、改稿、私下投稿或本地快照差异。

以上是本地统计与抽查，**没有调用模型给全量文章分类，也没有核对生产数据库**。具体口径见 `docs/plan/story-rebuild-research.md`。

### 2.2 “写死”应当写死什么

| 选择 | 好处 | 持续成本 | 建议 |
|---|---|---|---|
| 每篇正文直接写进独立 TSX | 自由度最大 | 改错字要改代码，版本难比对，容易把未获授权文本送进公开 Git | 仅对确实需要的少数特殊作品使用，且另确认入库授权 |
| 定稿正文 + 受控版式数据 + 少数定制组件 | 能逐篇设计，正文可核对，章节和素材可校验 | 需要先做好出版包与基础组件 | **默认采用** |
| 继续全靠目录扫描生成卡片 | 上新方便 | 缺少作品层级、策展与逐篇美术控制 | 保留为旧版兼容，逐步退出主入口 |

“定制页面”不等于“完全静态导出”。根布局现在读取登录用户，不能因为写了 `generateStaticParams` 就承诺整页成为静态 HTML。第一阶段目标是**确定的已审定版本、读取时不扫候选库、不调用 AI**。预渲染和缓存单独验证，见 `docs/plan/story-editorial-design.md` §6。

### 2.3 AI 与人分别决定什么

AI 做全文覆盖、内容类型建议、章序候选、证据摘录、摘要初稿、访谈问题、视觉方向和页面实现。站长决定选登、作者归属、来源与 AI 使用情况、推荐层级、公开范围；作者确认署名、定稿、改编尺度、配图与其意图是否一致。

**AI 生成、AI 辅助、转载、原创、是否值得推荐是不同维度。** 模型文风判断不能成为公开标记。Life 的小说按站长已提供的情况登记为待逐篇核对的已知线索，不把 Life 账号所有博客自动判成 AI 小说，也不把别的作者自动判成人类原创。

## 3. 最终产品的范围

### 3.1 读者看到的故事区

1. **故事首页**：一部主推、数部精选、明确的长篇/短篇/互动入口，以及完整作品目录。首屏直接展示具体作品与作者，减少从“小说集 1/2/3”逐层点进去的距离。
2. **作品首页**：封面、署名、无剧透简介、篇幅和连载状态；长篇有显式章序、开始/继续阅读入口；短篇可直接进入正文。
3. **阅读页**：稳定正文行宽、章节导航、目录、阅读位置、图片与文字有目的地组合；可切到纯文字阅读。
4. **专题或作者集合**：内容足够时再做，首发只需最小作者介绍和作品关联。
5. **旧版兼容**：没有重做的内容仍有可理解的去处；已迁移旧 URL 指向对应新版本，不能整批跳故事首页。

### 3.2 编辑端形成的长期资产

- 每条来源的版本、AI 建议和人工结论。
- 每部作品、每一章与多条来源之间的映射。
- 作者署名档案、授权范围和待核对事项。
- 经确认的编辑档案：摘要、主题解释、章纲、敏感情节与配图边界。
- 素材台账、设计简报、定稿出版包和可回滚发布记录。

这些资产可以导出，不能只留在一次聊天里。工具失效或模型更换时，人工结论与成品仍然能继续使用。

### 3.3 首版暂不建设

全功能投稿 CMS、自动文学评分榜、自动发消息给作者、全站自动查重爬虫、全量自动生图、每部作品一个完全不同的阅读器、推荐算法、音频朗读、电子书导出。它们都不是首版完成所必需。

## 4. 两条工作线与共同的发布关口

**内容工具线**负责发现和整理；**样板出版线**负责尽早完成可读成品。两条线可以交错推进，不必等批处理跑完整库。

```text
只读快照 ─→ 小样本人工标注 ─→ AI 初审与复审 ─→ 持续候选池
    │                                │
    └→ 旧故事与已知作者试点 ────────────┘
                      ↓
           作品/章节建档 → 作者确认 → 编辑定稿
                      ↓
             视觉简报 → 配图 → 页面样板
                      ↓
             出版包校验 → 预览签收 → 分批上线
```

任何来源都必须经过同一套定稿与发布检查。旧故事“已经展示过”不能代替新用途授权，AI 初审“通过”也不能代替人工选登。

## 5. 分阶段实施

工期按一位开发者配合站长估算，表示有效工作日，**不含等待作者回复，也不是承诺排期**。每阶段完成一个可验收的小闭环，随后再扩大。

| 阶段 | 主要工作与先后关系 | 交付物 | 结束条件 | 粗估 |
|---|---|---|---|---|
| M0 盘点 | 只读快照、旧路由清单、来源统计；确认不改原库 | 可重复运行的盘点命令、私有报告 | 排除软删；读到 WAL 一致快照；列清缺失/异常 | 1–2 日 |
| M1 复审最小工具 | 先定义分类与版本，再做导入、全文阅读、人工标记、导出 | 本地持久化工作台与人工标注集 | 关闭重开不丢；错误操作可撤回；能看全文而非仅摘要 | 3–5 日 |
| M2 AI 小批试验 | 用约 120 条分层样本试运行，冻结约 40 条独立验证；修改提示后重测 | 初审适配器、覆盖报告、误差报告、费用估算 | 重要漏检有解释与修正；运行可恢复；不同版本可比较 | 2–4 日 |
| M3 历史候选池 | 按预算分批覆盖 4,909 条；人工先处理不确定和重点候选 | 经人工确认的作品候选池，含未决项 | 任务账目闭合；负例有抽查；没有把失败当非小说 | 计算约 1–2 日历日；人工按批持续 |
| P1 样板编辑 | 从已知作品挑 3 个类型；做来源对照、章序、作者确认 | 3 份编辑定稿与设计简报 | 文本、署名、用途与禁忌清楚；无回复的作品可换候选 | 3–6 日，可从 M1 后开始 |
| P2 页面与美术 | 建阅读外壳、2–3 套版式；完成 1 短篇、1 长篇、1 互动样板 | 私有预览与完整出版包 | 三种阅读流程均可走完，素材可追溯，作者/站长签收 | 5–8 日 |
| P3 首发 | 策展首页、旧 URL 映射、sitemap 与发布/回滚演练 | 3 部完整样板；时间允许再扩到 6–8 部 | 首页每一项都能读，旧内容可达，撤回可执行 | 2–3 日 |
| O 持续运营 | 新增/改稿增量复审；每次发布少量作品 | 每周候选清单、每月小批选登 | 新增内容有稳定入口，不再积成几年一次的大整理 | 常态维护 |

M1 就要能独立使用，不能先造完全部 AI 调度器才允许人工读文章。M3 与 P1/P2 不互相等待。预算紧时先交付 M0、M1 和一个完整短篇样板。

### 5.1 下一轮开发的具体顺序

1. 建立最小字段和持久化存储，写只读盘点/导入器；默认无网络。
2. 做“左侧待办、右侧原文和结论”的工作台，支持保存、筛选、撤回、导出。
3. 导入旧故事并人工关联 Audrey、Connizarro、Efforia 的少量已知作品，验证一章多来源与一来源多章。
4. 用真实样本制作标注集，再接可替换的 AI 初审适配器；先跑 20 条检查，再跑评测集。
5. 同时选一篇有明确授权的短篇，完成编辑档案、定稿、无图版和一张图的出版演练。
6. 评测通过后扩大批次，并把短篇样板扩展为长篇和互动样板。
7. 最后替换故事首页和旧路由入口，逐部增加成品。

工具字段、队列与任务拆解见 `docs/plan/story-review-tooling.md`；作品制作步骤与交接模板见 `docs/plan/story-editorial-design.md`。

## 6. 首批试点怎么选

| 试点 | 能暴露什么问题 | 建议的第一步 |
|---|---|---|
| Efforia 的一篇短篇，例如旧故事中的《燃料》 | 博客版与整理版有差异；画面意象如何服务阅读 | 并排比对两版，请作者确认定稿；先试纯文字与少量意象插画 |
| 《阿提亚的四季童话》 | Audrey 账号与故事署名不同；旧文件合章、博客连载章序不同 | 建作者别名候选与章节映射，确认署名和最新章序，再试长篇目录 |
| Connizarro 的一个短篇或作品组 | “总归是物”在博客标题与旧合集里的含义未必相同 | 分清单篇/合集关系；按作品确认来源，避免按同名合并 |
| 一个现有 Cattca 故事 | 互动运行、分支和存档不能被普通图文重排替代 | 保留解释器，测试从开头到结局的实际路径 |
| Life 中一条已知小说 + 一条非小说 | 已知 AI 线索的登记范围、同账号混合类型 | 用于初审/复审校准，不默认放进首发精选 |

首发完成度优先于作者名额或作品数量。长篇无须等完结才能入选，但必须清楚标“连载”，不能把暂缺章节包装成完结作品。

## 7. 人力、费用和质量如何收住

### 7.1 不把人工从“读 5,000 篇”换成“审 5,000 张表”

工作台默认按作品候选与不确定项组织。已知重复内容可共享 AI 分析，但保留每次投稿的来源与作者；疑似同一连载可整组查看，批量动作必须预览影响范围。

假设初审后有 400 条候选、每条快速复审 2 分钟，就是约 13.3 小时；若是 1,000 条则是约 33.3 小时。**400 和 1,000 都是容量情景，不是本次识别出的小说数。** 长篇完整阅读、作者沟通和定稿另外计时。先记录 30 条真实操作耗时，再制定每周可承受的处理量。

建议每周两个 45 分钟的复审时段，每月集中制作 1–3 部作品；站长只对需要判断的节点做决定，AI 和工具负责资料整合与重复劳动。

### 7.2 先测费用，再下全量任务

不以中文字符直接折算账单。小批试验记录实际输入、输出、分段重叠、重试和更强模型升级的 token；按任务层分别外推全量费用。分类用较经济模型，疑难项升级，详细编辑分析只对入选作品做，生图只在简报通过后开始。

每批显示预计费用、预算上限、已用金额和未完成量；预算到线停止创建新请求，已返回的结果照常归档。可用异步 Batch 降低非实时任务成本，但模型、端点、保留策略与价格在实施时重新核对。[OpenAI Batch 官方文档](https://developers.openai.com/api/docs/guides/batch)

### 7.3 判断是否做成

| 范围 | 最低可验收标准 |
|---|---|
| 发现 | 每条来源明确记录已处理、失败、未处理或待人工；长文有覆盖报告 |
| 初审 | 冻结样本报告候选召回、精确率、难例和不确定比例；高置信负例仍抽查 |
| 复审 | 人工结论不被重跑覆盖；每个公开标记有证据与确认人 |
| 编辑 | 每部上线作品有来源映射、定稿、授权范围、无剧透简介和版本号 |
| 视觉 | 图片与版式支持作品，纯文字阅读完整；手机、明暗主题、缩放与键盘可用 |
| 发布 | 旧 URL 有去处、目录章序正确、匿名只能读已公开版本、能下架与回滚 |
| 运营 | 新投稿和改稿能增量进入流程，上一轮人工工作可复用 |

## 8. 待决定的事项与建议默认值

| 事项 | 建议默认值 | 何时必须定下来 |
|---|---|---|
| AI 小说的地位 | 可单独保留“AI 创作”集合，不自动进入主推；与人类原创分标签陈列 | 首页选编前 |
| 转载作品 | 未确认来源与展示许可前仅留编辑候选；不进入“站内原创”口径 | 每部作品出版前 |
| 作者无回复 | 暂存原有已授权范围，不新增改编和公开用途；换可确认的试点 | 样板选择时 |
| 正文是否进公开 Git | 默认不进；版式代码可入库，正文与授权凭据单独存放 | 生成第一个出版包前 |
| AI 分析范围 | 工具默认离线；确认处理范围与服务商后，才发送所需正文 | 第一次联网分析前 |
| 评论和互动 | 首版保留到原博客的可用链接，不复制评论、不合并点赞 | 阅读页开发时 |
| 发布规模 | 先 3 个完整样板，再 6–8 部首批；不追求一口气搬空旧合集 | 首轮排期时 |
