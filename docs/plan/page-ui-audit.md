# 功能页面 UI 调研报告

校对日期：2026-10-30。状态：**调研完成，界面改造未实施，建议范围待决定**。

## 1. 判断与调研边界

建议做一轮以**页面骨架、操作层级、桌面空间利用**为中心的局部 UI 整理。
用户指出的小鱼干、市场、设置、签到，确实能找到具体的结构问题；同类问题还出现在
商城、投票列表、鱼干接口、联系页，以及部分空状态和前置条件引导中。

这些页面已有主题色、圆角、按钮与间距规则。“简陋”的主要来源是：已有组件之间的
关系表达不足，页面经常呈现为“一张窄卡片”“一列同样的卡片”或“一串居中操作”。
改善重点应放在内容如何组织、哪些信息先看、下一步在哪里。

### 1.1 本轮证据

- **源码基线**：本地 `main`，开始调研时 HEAD 为 `b6138866`。扫描 108 个
  `page.tsx` 路由文件的分布，重点读取下表页面、相关组件及 SCSS；并非对 108 页逐一视觉验收。
- **浏览器实看**：通过仓库现有 `probe:page` 在本地开发服务读取 `/fish/market`、
  `/contact`，均返回 200；截图为 1280 × 720、浅色主题、匿名状态。
- **登录态限制**：本地开发服务不接受探针的 core 种子账号（401）。小鱼干账户、
  商城、设置、签到等登录态页面的判断来自当前 JSX、状态分支和样式，未冒充浏览器实测。
- **工作区边界**：调研开始时有其他未提交改动。本报告不将它们当成缺陷，也未修改或提交那些文件。
- **未覆盖**：生产站点与本地版本的一致性、真实账号数据、深色主题截图、手机实机和完整交互流程。
  本文的“480px”等数值是源码上限；除上面两页外，没有声称测得实际元素几何。

## 2. “简陋”可以分成哪几种

| 类型 | 用户会看到什么 | 当前代表 | 对应改造方向 |
|---|---|---|---|
| A. 整页被局部限宽 | 电脑上主体像一张手机卡片，和顶栏、其他页面缺少共同边线 | 小鱼干、设置、投票列表 | 统一外壳，字段和阅读区域再在内部限宽 |
| B. 有宽度，没有空间组织 | 页面很宽，内容仍集中在中轴，四周空白没有表达关系 | 签到；旧市场选择页实看 | 将主任务、状态、辅助内容按关系分区 |
| C. 操作长得太相似 | 执行动作、已完成结果、跳转入口都像同一类胶囊，难以一眼判断先点什么 | 签到完成态、未发文引导；部分页尾链接 | 区分主操作、状态、功能导航和返回 |
| D. 内容只会向下堆 | 一个商品一整套租期表单、一项设置一张大卡，越长越像组件清单 | 商城、设置 | 按任务组织密度；浏览、选择、编辑各有位置 |
| E. 页面缺少稳定框架 | 标题在卡内或页外、居中或靠左各自决定；返回入口落在页面末尾 | 鱼干各子页、联系页 | 统一页头与导航落点，保留各页主体差异 |
| F. 状态说明不完整 | 空数据像没加载出来；默认值像已读取的真实设置 | 商城无商品、设置资料加载失败 | 明确加载、空、失败、成功和下一步 |

六类经常叠加。例如小鱼干同时有 A、C、E；签到主要是 B、C。
“窄”与“宽但空”需要不同处理；单改一个 `max-width` 只能解决其中一部分。

## 3. 宽度问题的具体来源

本站普通页面的既有阶梯是：小于 992px 使用可用宽度，992px 起上限 960px，
1200px 起上限 1140px，左右内距 16px。依据是 `docs/frontend-styles.md` §4.1，
实现为 `src/styles-scss/abstracts/_mixins.scss` 的 `site-width-ladder`。

| 页面 / 区域 | 当前源码 | 判断 |
|---|---|---|
| `/fish` | 外层 `.container` 遵循阶梯；内部 `.fish-card` 上限 **480px** | 页面外壳正常，承载全部内容的卡片过窄 |
| `/fish/transfer` | `.content-wrapper` 遵循阶梯；`TransferPanel` 的 `.market-card` 上限 **480px** | 表单宽度可保留，但页头、导航不应一起呈现成孤立小岛 |
| `/fish/shop` | 外层遵循阶梯；每款商品都是 **480px** 的 `.market-card`，直接逐项输出 | 桌面仍逐款纵向排，缺少商品浏览布局 |
| `/settings` | `.settings-page.container`；页面规则将上限覆盖为 **700px** | 限制发生在整页，导航和所有分组一起被压窄 |
| `/vote` | `.vote-page` 上限 **720px** | 作为列表入口偏窄；投票表单、详情应另按阅读需要判断 |
| `/checkin` | `.checkin-page` 已复用完整容器阶梯 | 当前源码里没有“签到整页太窄”的同一原因，核心在内部组织 |
| `/fish/market` | 旧地址壳使用完整阶梯，两颗导航按两列等分 | 实看已够宽，反而形成两块被拉开的超宽入口和大片空白 |
| `/fish/api` | 外层完整阶梯；主体为 `.fish-api-section` | 当前主体没有继承 480px 卡片上限，应查分区和信息层级 |
| `/quotes/*` | 共享页壳上限 **940px** | 主要是阅读任务，有合理解释，暂不强制拉到 1140px |
| `/contact` | 外层完整阶梯；联系列表内联上限 **560px** | 信息量少，560px 本身可接受，问题在内容组织和视觉完成度 |

关键证据：`src/styles-scss/pages/_fish.scss` 第 8–18 行；
`src/styles-scss/pages/_fish-market.scss` 第 23–30 行；
`src/styles-scss/pages/_settings.scss` 第 8–15 行；
`src/styles-scss/pages/_vote.scss` 第 6–14 行；
`src/styles-scss/pages/_checkin.scss` 的 `.checkin-page`；
`src/styles-scss/pages/_daily-quote.scss` 的 `.daily-quote-page`。
样式先后顺序在 `src/styles-scss/main.scss`，布局规则早于页面规则，因此设置的 700px 会生效。

建议明确两层宽度的职责：

- **页面外壳**：普通功能页的页头、导航与主区域，采用既有 960 / 1140px 阶梯。
- **任务内部**：单个密码表单、付款确认、说明正文控制行宽；商品目录、账户操作、
  多区工作台按空间分列。限制字段宽度无需缩窄整页。

阅读页、登录授权页和单次支付任务可以继续紧凑。统一的目标是可理解的布局规则，
无需让每张卡片具有相同宽度。

| UI-12 / P2 | 商城空内容、设置加载失败 | 商城 `items.length === 0` 直接返回 `null`，分类无匹配也没有专门结果；设置读取异常保留默认资料值 | 商城解释当前无商品 / 无匹配并保留分类；设置显式区分加载、失败、重试与已读取数据，失败时避免把默认项当真实设置展示 |

### 4.1 签到的“按钮串”具体在哪里

`src/app/components/CheckinCard.tsx` 的顺序是：问候 / 日期 → 签到按钮 → 累计天数 →
完成后才出现的“查看今日一言”。`src/app/checkin/page.tsx` 随后再输出“每日一言”入口，
然后是榜单。`.checkin-card` 设置 `text-align: center`；
`.checkin-quote-links` 进一步设置 `justify-content: center`。

当前版本已经减少了原来的多个一言子页入口，但**完成态仍有三个不同性质的对象连续居中**：
已签到结果、打开今日内容、前往完整功能域。它们不必都采用近似按钮的呈现。
未发文状态的两颗引导按钮则是另一条需单独校准的分支。

可以保留签到的轻量庆祝反馈。首先改善静态版面和完成态的主次，动效再跟随状态转换；
不需要增加新的循环装饰。

### 4.2 设置并不是“完全没分组”

设置本轮已存在有名称的 `section` 和 h2 / h3。问题是页面整体仍按短表单的宽度组织，
分组导航只出现在顶部，长内容没有利用桌面方向建立持续定位。
继续添加分组标题的收益有限，优先改变目录和内容的空间关系。

资料读取失败保留默认值见 `src/app/settings/page.tsx` 的首次 `useEffect`。
这是源码可确认的状态表达缺口，本轮未模拟网络失败，未声称复现用户误操作或数据覆盖。

### 4.3 商城的主要成本是重复完整表单

`src/app/fish/market/ShopPanel.tsx` 直接遍历过滤后的商品输出 `ShopItemCard`，
每款卡片都使用 `.market-card`。商品数量增长时，重复的租期、合计和提交区域会拉长浏览路径。
当前分类和共享余额已经存在，应在此基础上改排版。

“先做网格、保留原表单”是成本较小的首轮候选；“选择商品后展开租用区”会涉及更多状态、
焦点和测试，留作第二步评估。租期单位、二次确认、持有状态与服务端购买规则继续保持一致。

## 5. 哪些页面不宜被这轮一起重做

| 页面族 | 本轮观察 | 建议范围 |

这些是本轮范围判断，不代表上述页面已经完成完整视觉或无障碍验收。

## 6. 建议的首轮重构范围

### 6.1 先收敛页面外壳

将既有规则组织成少量可复用的组合：页标题与页级操作、功能域导航、主体区。
可以复用 CSS 和轻量组合组件；无需先引入新的 UI 库或重写所有页面。

普通功能页沿用容器阶梯。设置目录、账户摘要、商品目录、列表工具栏各有相应版式；
字段在内部设上限。具体实现继续遵循 `docs/frontend-styles.md` 与 `docs/design-philosophy.md`：
底色和留白承担层级，按钮沿用三档，文字只解释功能和状态。

### 6.2 三个重点页面的结构草案

以下只表达空间关系，不是已实现的设计稿。

| 页面 | 电脑 | 手机 |
|---|---|---|
| 小鱼干 | 共同页头；余额摘要与常用操作形成主区；商城 / 练手盘形成次级入口区 | 依次呈现摘要、常用操作、次级入口；操作保持可点且文字完整 |
| 签到 | 今日任务主区与榜单辅助区并列；完成态显示到账结果及查看一言；完整一言入口归导航 | 主任务先出现，榜单后出现；签到结果不与跳转入口争夺同等权重 |
| 设置 | 左侧分组目录与右侧设置内容；目录在长页中持续可达；每组字段保持合理行宽 | 同一内容顺序；目录折为紧凑页内导航，不把长表单硬塞成两列 |

账户第一版可以只重排已有余额和入口，不新增收益图、活动通知或虚构统计。
如果后续确实需要近期流水预览，应作为单独的数据读取扩展评估，不能为填满空白随意加指标。

### 6.3 分批交付

| 批次 | 范围 | 预期收益 |
|---|---|---|
| 第一批 | 小鱼干账户、签到、设置、商城；抽取必要的页壳与导航组合 | 覆盖用户最明确的不满，同时建立可复用版式 |
| 第二批 | 转账、流水、鱼干接口、旧市场兼容壳、投票列表；补齐 UI-12 状态 | 消除同一功能域中的布局断裂和空白失联 |
| 第三批 | 联系页及其他页面的页头、空状态局部校准 | 提升边缘页面完成度，避免将低频页面扩大成大工程 |

第一批可以逐页提交。每页先完成桌面与手机静态组织，再检查加载、成功、失败等分支，
最后校准动效。无需同时重写权限、账本、接口或站点全局主题。

## 7. 后续验收口径

下面是实施后的验收要求，**不是本次已经通过的测试结果**。

1. **桌面外壳**：在 1440、1280、1024px 下，普通功能页的页头与站点容器对齐；
   保留紧凑表单时，必须能分清页面外壳与局部字段宽度。
2. **空间利用**：账户不再由一张孤立的 480px 卡片承担整页；商城能在空间允许时并列商品；
   签到主任务与榜单的关系清楚；设置长页中能持续找到分组。
3. **操作主次**：未签到、已签到、未发文三个状态分别检查；能一眼识别当前可完成的主任务。
   结果、导航、返回不再机械地重复主按钮外观。
4. **窄屏与缩放**：在 768、390、320px 检查折列、长文本和页面横向溢出。
   普通内容应能重排；需要二维布局的表格 / 图表只在局部滚动。依据
   [W3C 对 Reflow 的说明](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)。
5. **标题与定位**：标题准确表达所在任务，模块标题与字段标签区分清楚；共同导航标出当前位置。
   “标题和标签描述主题或用途”是可用性的基本判据，见
   [W3C 对 Headings and Labels 的说明](https://www.w3.org/WAI/WCAG22/Understanding/headings-and-labels.html)。
   本报告未据此进行 WCAG 合规判定。
6. **完整状态**：覆盖无商品、分类无结果、无流水、资料加载失败、余额不足、提交中、成功与失败；
   已实现的状态继续复用，新增布局不能把它们藏掉。校准浅色 / 深色、键盘焦点及减少动态效果。
7. **回归边界**：先阅读对应 e2e 再修改 DOM。`tests/e2e/fish-layout.spec.ts` 约束账户入口、
   至少 44px 操作高度、溢出、旧市场兼容与练手盘导航；收银台 / 收款页还被相关流程用例约束。
   收藏夹有专门几何契约。应按当前用例核对，不能照旧注释猜固定按钮数量。

本站 44px 等具体操作尺寸来自仓库已有设计与测试约定；上面的外部资料仅辅助解释重排与定位，
不替代本站样式规范。本文的优先级和布局草案是基于当前源码与有限实看的设计判断，
后续应以登录态桌面、手机截图和真实任务走查完成视觉确认。
