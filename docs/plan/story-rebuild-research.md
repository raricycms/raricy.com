### 2.1 总量

| 原始长度中位数 / P90 / P99 | 113 / 3,372 / 160,751 |
| 最大原始长度 | 199,637 |

P90、P99 使用排序后下标 `floor(n × p)` 取值。来源时间戳为历史数据库里的毫秒数，只有日期用于判断快照覆盖范围；后续工具应沿用项目 `src/lib/db-time.ts` 的时间语义。

核心汇总可在只读快照中用下列 SQL 复核；长度分位、段落匹配和文件数另外按上面的口径统计，不把这些查询当正式迁移脚本。

```sql
SELECT COUNT(*) AS total,
       SUM(CASE WHEN ignore IS NULL OR ignore = 0 THEN 1 ELSE 0 END) AS active
FROM blogs;

SELECT b.visibility, bc.format, COUNT(*) AS posts,
       SUM(LENGTH(bc.content)) AS raw_chars
FROM blogs AS b
LEFT JOIN blog_contents AS bc ON bc.blog_id = b.id
WHERE b.ignore IS NULL OR b.ignore = 0
GROUP BY b.visibility, bc.format;
```

### 3.2 为什么不能简单同步博客

匹配方法：对 265 个 `.md` 去掉平铺 frontmatter，对正文去空白，与未删除博客正文去空白后比较。只有 8 个故事文件存在全文相同的博客来源。这是**严格相同检测**，不是模糊匹配，不包含标题/标点消除、段落包含或合章匹配。

《阿提亚的四季童话》的旧合集作者字段与 Audrey 账号不是同一个显示名；博客有八条连载，故事文件仅两个。《燃料》两边的开头情节对应，但分隔与正文整理有差异。由此可确认需要“多来源 → 编辑版本”的映射，不能让一个 `blogId` 字段承担全部关系。

新版导入器要生成候选映射与差异，再由人确认，不能自动覆盖旧故事，不能把匹配失败说成失去版权依据，也不能把上传账号写成最终作者。

### 4.1 页面观察与设计判断

本地桌面页面确实把八个合集渲染成近似规格的大卡片；读者第一眼看到的是“互动小说/小说集 1/2/3”等分类，而不是具体作者与作品。缺封面和编辑推荐层级，与“小说区只是文件目录”的数据形状一致。

这是本次设计判断，不是性能测试结论。首屏改成具体作品、缩短读到正文的路径，比给原有八张卡片换一套渐变更能解决门面问题。未实测的手机、深色和长篇阅读问题，留到样板验收处理。

## 5. 可复用的能力与边界

- `scripts/reactive-corpus-report.mjs` 已采用显式输入/输出、SQLite 只读、不自动读取生产环境的方式，适合借鉴导入纪律；它做语法风险报告，不是小说筛选器，也不能当现成的 AI 服务。
- 已有后台壳、角色判定、CSRF、审计和 Markdown/ReactiveMD 安全处理能力。新工作台复用它们，但必须另设 owner 级页面与接口权限；后台父布局只要求 core，不能依赖它兜底。
- 博客与正文分表，`blog_contents.updated_at` 不是所有元数据变更的统一修订号。增量同步还要检测标题、作者、可见性、软删和格式等变化。
- 代码支持 ReactiveMD；这份本地快照均为 Markdown，不能据此假设后续数据永远如此。格式未知/转换失败明确进人工队列，不能当非小说。
- 项目已有公开正文搜索。编辑工具可以借鉴文本提取方式，但不能把站内作品、剧透摘要或工作台评语并入公开搜索索引。
- 第三方素材默认不入库；站长自行制作且有权公开的资产可入库。正文、图像、字体、作者私信的授权必须分开记录。

## 6. 外部调研与适用范围

以下资料查阅于 2026-10-31；模型价格、额度与接口细节实施时重查。只引用与决策相关的结论。

1. **异步分类可以降低成本。** Batch 文档提供异步批处理、相较同步请求的 50% 折扣、24 小时完成窗口；返回结果依赖自定义 ID 关联，不应依赖行顺序。项目据此设计可恢复批次，而不把 24 小时当整个整理项目的工期。[OpenAI Batch](https://developers.openai.com/api/docs/guides/batch)
2. **结构化输出约束形状，不能担保判断正确。** 严格 schema 仍需本地字段/证据/覆盖校验，以及拒答、截断、错误的独立状态。[OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)
3. **默认不用于训练不等于零留存。** 官方区分滥用监测日志与应用状态；批处理、文件等有独立保留政策。项目不承诺 `store: false` 能消除所有留存，先决定处理范围与清理策略。[OpenAI 数据控制](https://developers.openai.com/api/docs/guides/your-data)
4. **文本检测器有误判与规避问题。** Weber-Wulff 等人在 2023 年对当时 14 套工具的研究发现可靠性局限。该结果不是对 2026 年所有检测器、中文小说的统一精度测量；本计划的产品选择是“不把文风或检测分数作为公开 AI 定性依据”。[原始研究](https://arxiv.org/abs/2306.15666)
5. **定制图应允许局部修订。** 图像 API 提供生成与编辑能力，适合先建立角色/场景基准，再对获选构图迭代；这不保证跨图角色自动一致，仍须人工检查。[OpenAI 图像生成与编辑](https://developers.openai.com/api/docs/guides/image-generation)
6. **框架提供构建期路由枚举，但有条件。** Next.js 15 的 `generateStaticParams` 用来枚举构建期路由；本站登录态根布局等动态依赖要另行处理，不能为预渲染把当前用户变空。[Next.js 15 官方说明](https://nextjs.org/docs/15/app/api-reference/functions/generate-static-params)
7. **图片按用途写替代文本。** 信息图像提供必要含义，纯装饰图使用空替代文本。对小说还要检查 alt 是否提前剧透。[W3C WAI 图片教程](https://www.w3.org/WAI/tutorials/images/)

## 7. 仍不知道的事

全站真正有多少独立小说、同人/转载/AI 各有多少、每个连载的当前完成度、哪些作者愿意公开选登与允许 AI 配图、生产环境缺哪些本地文件，均未在本次确认。

下一步用工具与作者确认逐渐回答，不用模型一次性猜出“最终作品总表”。每次导入、复审与发布都保留日期、来源版本和未决项，避免这份静态调研几个月后再次被当成实时事实。
