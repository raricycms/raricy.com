# 每日一言修复方案（待审查）

调研日期：2026-10-29。代码基线：`ca46e5a3`。状态：**方案待审查，功能尚未修改**。

## 1. 建议审查的结论

建议把每日一言补成一条完整的使用路径：**签到看今日 → 往期列表回看 → 随时共鸣或收藏 → 在私密一言集中重读**。

| 问题 | 建议结果 |
|---|---|
| 昨天没有收藏，今天就找不到 | 新增「往期一言」，列出系统实际选用过的日期和内容；无需当天签到即可回看 |
| 收藏后隔天又能共鸣 | 改为同一用户对同一句一言累计只能共鸣一次，不随换日、取消收藏或再次入选重置 |
| 弹窗和列表像简单拼装，缺少整体感 | 分开设计今日阅读弹窗与往期列表，共用内容与互动状态，采用本站的容器、卡片、胶囊导航和分页 |

本方案的三个产品取舍供整体审查：

1. **历史面向所有 core+ 用户开放**，不要求那天来过或今天已签到；今日内容仍保留签到后查看的规则。
2. **共鸣累计一次且不可撤销**；站友稿件首次共鸣扣 1 条鱼干，经典仍免费。收藏独立、可取消。
3. **旧重复记录和鱼干流水全部保留，不自动退款**；界面共鸣数改为去重人数。旧规则下发生的转账不直接改账，如需补偿，应另定范围。

后文描述的是拟实施行为，不代表当前已支持。

## 2. 调研范围与证据

本轮检查了页面、组件、服务、HTTP 路由、Prisma 模型、建表迁移、使用指南、样式规范及现有测试。

本轮没有在浏览器中完成视觉验收；当前生产数据量、历史缺日数及重复扣款涉及人数仍未知。

### 2.1 “重复共鸣”能确认到什么程度

**已从代码和测试确认：跨日可重复。** 收藏与共鸣没有因果关系，只是一言集让旧句子一直可访问，
更容易触发这个旧规则。即使从其他入口访问同一条已发布一言，服务端也允许跨日再次共鸣。

**现有实现对同一天的重复已有防线**：请求前查重、数据库三元唯一约束、扣款与入账同事务；
现有服务测试还覆盖并发重复请求。因而不能仅凭反馈认定同一天也能反复扣款。
若后续仍收到同日重复报告，需对照具体时间、quoteId、用户及流水进一步归因。

### 2.2 目前的视觉问题

现有代码已经使用主题变量、公共按钮 mixin、30px 弹窗、Lucide 图标及焦点恢复，
不需要推倒整套视觉基础。主要问题在信息组织与复用方式：

- **缺少功能主页面**：今日弹窗、一言集、投稿页彼此分散，用户难以形成「每日一言在哪里」的认识。
- **列表直接套用弹窗卡**：每条重复分类、来源、完整费用说明和一条常驻反馈空行，列表密度低。
- **正文空间被多层内距消耗**：收藏列表有页面、外卡和引文底块三层；外卡桌面 28px、引文再 24px，
  窄屏外卡 20px、引文仍 24px。层级本身符合主题色，但列表中的层层套块显得笨重。
- **缺少日期上下文**：内容契约只给 quoteId，一言集不显示它是哪一天入选，难以和「每日」对应。
- **导航和分页未形成统一体验**：相关入口零散；一言集只有手写上一页 / 下一页，未使用公共 `SitePager`。

## 3. 历史与权限规则

### 3.1 历史究竟列什么

新增页面拟为 `/checkin/quotes`，标题「往期一言」。数据来源是 `daily_quote_editions`，
以日期倒序，每页 20 期；首版只提供稳定分页，不叠加搜索、排行榜或分类筛选。

- 每个真实存在且 `day < todayStr()` 的选用记录是一条历史。
- 不要求用户当天签到、曾看过或已经收藏；新加入的 core+ 用户也可回看全站往期。
- 不公开整个审核通过的候选池。已通过但从未入选、待审和被拒稿件均不进入历史。
- 当前是惰性选句：只有首次读取今日一言才创建当天记录。因此某天没有选用记录，历史也没有该期；
  不伪造过去的抽签结果，不用今日候选补齐空白日期，分页总数按实际期数计算。
- 同一句在 90 天后再次入选，保留两个日期条目，互动状态和共鸣总人数按 quoteId 共用。
- 已下架或作者已归档的内容保留日期及不可用占位，不显示原文、出处或身份，不允许新增共鸣 / 收藏。
  本人已收藏的不可用内容仍可移出一言集。

历史查询是纯读取，**不调用 `selectEdition` 或 `getTodayQuote`**，不会为今天或过去补抽。

### 3.2 今日与历史的边界

| 场景 | 查看与操作 |
|---|---|
| core+，今天未签到 | 可以查看、共鸣、收藏往期；今日内容继续要求签到 |
| core+，今天已签到 | 可以打开今日弹窗，也可以浏览往期与一言集 |
| 没有发过文章，尚不具备签到条件的 core+ | 可以浏览和操作往期；不因此获得签到资格或签到奖励 |
| 未登录 / 普通用户 | 沿用登录引导 / core+ 权限限制；页面和接口各自校验 |
| 禁言中的 core+ | 历史与一言集保持只读，投稿、共鸣和收藏变更由服务端拒绝 |
| 投稿人当前无法接收投喂 | 已发布内容沿用现有可见性规则；未共鸣者看到不可投喂原因，不能扣款 |

新历史页排除今天，避免成为绕过签到的今日读取入口。历史的共鸣和收藏本身不需要签到，
这与现有写接口只校验「已发布内容」的方向一致；不得给历史操作另加今日签到门槛。

### 3.3 入口安排

- 签到页在签到状态分支之外提供「往期一言 / 一言集 / 我的投稿」，未签到和未满足发文条件时也能找到。
- 今日弹窗底部保留「往期一言」「一言集」和「我也要投稿」；「我的投稿」入口集中在相关页面导航与投稿成功态。
- 往期页、一言集、我的投稿使用同一组页面导航，并标明当前项。保留各页现有业务用途及地址。
- 收藏夹主页保留原有「一言集」入口；一言集空态增加前往往期的操作，用户无需等下一次签到。

## 4. 共鸣累计一次与旧数据处理

### 4.1 新的不变量

1. `(quoteId, userId)` 一生最多一次有效共鸣；日期仅记录发生时间，不参与权限和去重。
2. 换日、刷新、重启、取消 / 重新收藏、再次入选，都不恢复共鸣资格。
3. 已共鸣不提供取消操作；重复请求返回幂等成功，不增加人数或产生鱼干流水。
4. 社区稿件仍由付款者支付 1 条鱼干并全额交给投稿人，经典不扣款；不能对自己共鸣。
5. 共鸣资格、记录、两侧记账在同一事务处理；余额不足或作者入账失败时全部回滚。
6. 收藏完全独立：没有共鸣也能收藏，取消收藏也不会撤销或重置共鸣。

### 4.2 数据库实施建议：新增累计去重表，保留原始明细

不能直接给旧表加 `(quote_id, user_id)` 唯一索引：存量跨日重复可能使迁移失败。
也不应通过删除重复行完成迁移，那会丢掉真实行为记录，并破坏记录与历史转账的对应关系。

建议新增 `daily_quote_resonance_once`，作为累计资格与人数的唯一依据：

| 字段 | 用途 |
|---|---|
| `quote_id`、`user_id` | 联合主键，数据库保证累计只生效一次 |
| `first_resonated_at` | 从该组合最早的旧记录回填；新共鸣使用 `nowForDb()` |

原 `daily_quote_resonances` 保留日期、paid_units 与每次发生的明细。迁移用按用户和语录分组的
`MIN(created_at)` 回填新表，使用可重复执行的建表及冲突忽略插入；由既有迁移跟踪流程管理。
**不改写旧迁移、不删原表、不改鱼干余额或流水。** 具体迁移编号实施时按仓库最新序号确定。
回填涵盖归档用户的旧记录，避免恢复账号后重获资格；普通人数查询仍沿用账号归档边界。

切换后的新共鸣，在一个事务内依次完成资格复核、写累计去重行、写原明细行、付款与收款记账。
任何步骤失败全部回滚。并发冲突时仅在累计记录确实存在后返回「已共鸣」，不能吞掉其他约束错误。
新表与明细表的关系要写入服务头部，并覆盖测试辅助库的清理顺序与外键关系。

读本人状态统一查询新表，不再传 day；总数统一统计新表中的人数。原始明细只服务历史审计，
不再用它的行数决定按钮状态或显示人数。新增表对账号归档、只读统计和管理员工具的影响一并检查。

### 4.3 存量重复的产品呈现

例如，同一人过去三天给一句话各共鸣一次：

- 三条旧共鸣明细和实际发生的鱼干流水都保留。
- 累计去重表只有一行；该用户以后一直显示「已共鸣」。
- 这位用户对界面总数贡献 1 人，而非 3 次。因此某些内容上线后显示的共鸣数可能下降。
- 使用指南与更新说明明确新口径，必要时把数值的可访问名称写成「共鸣人数」。

上线前应只读统计重复组合数、涉及付费次数和金额，确认影响；该统计不是本轮已完成的生产审计。
如用户希望退还旧重复投喂，需另行设计有审计依据的补偿流程，不删除历史流水。

### 4.4 接口与前端状态

保留现有共鸣 POST 地址和 `already_resonated`，扩充响应为服务端确认的 `resonated`、
`can_resonate`、`resonance_count` 等状态；保留余额字段的既有兼容性。
客户端不再仅凭本地旧数值 `+1` 猜总数，两个标签页都共鸣后也能取得权威结果。

文案统一使用「已共鸣」「每人每句限一次」；删除「今天已经共鸣」「今日已共鸣」「每天限一次」。
已共鸣状态的说明优先于作者当前不能收款的提示，避免让用户误以为作者恢复资格后还能再付一次。

共享卡片的状态必须能接收刷新后的服务端数据。目前 `useState(initialQuote)` 只吃首次值，
新增历史列表后要处理同一组件未卸载时的数据更新，并让同页重复入选的同一句按 quoteId 同步。
跨页或跨标签页在下次加载 / 交互后以服务端结果收敛，不为这一功能新增实时连接。

| 现有写路由 | 共鸣地址不变；收藏语义不变；保持禁言、已发布、同源与匿名边界 |
| 展示组件 | `DailyQuoteCard` 区分今日 / 列表模式；历史列表以 quoteId 同步互动；更新 `SavedQuotes`、弹窗和入口 |
| 样式与分页 | 在 `_daily-quote.scss` 内收拢专属布局，复用公共 mixin、主题变量和 `SitePager` |
| 当前行为文档 | 实施后更新使用指南、架构 §6.22 以及本计划的交付状态与验证证据 |

历史接口建议返回 `{ page, pages, total, editions: [{ day, quote_id, quote }] }`，
`quote` 使用统一展示契约，不可用内容返回 null；不返回投稿人账号 ID、审核理由或共鸣用户名单。
页码非正整数退回第一页，超过最后一页时归一到有效末页；无数据时 `page=1, pages=0`。

每页 20 期需要批量查询内容、投稿人可收款状态、本人累计共鸣、本人收藏及共鸣人数。
现有 `quoteView` 每条再发多次查询、`listSavedQuotes` 再逐条读取内容，不能直接扩成历史列表的 N+1 查询。
今日读口也调用同一组装逻辑，避免两种入口对匿名、下架和共鸣状态给出不同结果。

历史页和接口都是只读入口，SSR 页面可直接调用服务；API 供刷新和后续客户端加载复用。
首版不为分页增加无限滚动，不引入额外定时任务、第三方依赖或新的鱼干获取渠道。

## 7. 验收用例

| 编号 | 必须满足的结果 |
|---|---|
| H1 | 昨日未收藏的内容今天仍出现在历史里，可直接收藏和共鸣 |

不能只修改断言数字。迁移用真正含重复数据的 SQLite 夹具验证；浏览器用例实际从历史入口操作往期，
覆盖未收藏、未签到和跨入口状态，不只检查按钮是否出现。
